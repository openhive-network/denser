# Logged-in vs logged-out page performance (2026-10-07)

The integration Lighthouse check (`stack/integration/lighthouse.sh`) measures anonymous
visitors only. This records one measurement of the same kind of pages for a logged-in
reader, against the integration site at `8d3fcbf3` (after #1040–#1052, #1042, #1045,
#1047, #1049, #1059, #1062, #1063).

## Method

- Site: https://denser.discuss.peerverity.info (follow mode, live Hive API).
- Lighthouse 13.5, mobile defaults (simulated throttling), in the image the integration
  check uses, driven through its Node API with puppeteer-core, `--cpus 2 --memory 2g`,
  run from steem-17.
- Logged in = the state denser's Keychain login leaves behind: the `observer` cookie and
  the localStorage `user` entry, for `blocktrades`. No key was used. Lighthouse's storage
  reset was disabled so the login survives.
- Three runs per route and mode, alternating logged out / logged in, so both modes saw the
  same API conditions. Medians below. `/wallet/~witnesses` has 2 / 1 runs (the run ended
  early on an out-of-memory error in the measuring process).
- Simulated LCP here is lower than in the integration check, because the measuring host is
  faster. Compare the two modes with each other, not with the check's numbers.

## What the difference is

On a logged-in `/blog/trending` the browser loads 8 more script chunks (284 KB transfer)
and the wax WASM (`wax.common.*.wasm`, 966 KB), which a logged-out visit doesn't load:

| chunk | transfer | contents |
|---|---|---|
| `1-zcb1mhnwqek.js` | 162 KB | wax, beekeeper, zod, hb-auth client, Keychain and HiveAuth signers |
| `3mfi0rd0mms1g.js` | 67 KB | wax `createHiveChain`, notifications |
| 6 more | 55 KB | zod, small helpers |

So a logged-in reader pays about 1.25 MB more at startup for the signing stack, before
signing anything. Total blocking time roughly doubles on every route; the post page goes
from 437 to 1,029 ms.

The extra API requests are per-user reads, and expected: `database_api.find_accounts` (2),
`bridge.get_follow_list`, `bridge.unread_notifications`, `bridge.get_profile`,
`database_api.get_dynamic_global_properties`, `rc_api.find_rc_accounts`.

## Logged-in thresholds of the integration check

The integration check now measures logged-in mode too (`integrationLoggedIn` in
`scripts/ci-helpers/lighthouse-thresholds.json`). Its limits start from this measurement:

- **Time (LCP, TBT):** the measuring host here was faster, so the evidence is the ratio
  of the two modes, not their values. A logged-in limit is the logged-out limit of the
  route times that page type's ratio, rounded up to a tenth and never below 1 (LCP rounded
  up to 500 ms):

  | page type (routes) | LCP | TBT |
  |---|---|---|
  | feed: `/blog/trending`, the community feed, `/blog/@gtg` (another's profile) | 1.1 | 2.4 |
  | post: the two post pages | 1.0 | 2.4 |
  | own profile: `/blog/@{observer}`, from `/blog/@gtg`'s limits | 2.2 | 2.4 |
  | notifications: `/blog/@{observer}/notifications`, from `/blog/@gtg`'s limits | 1.0 | 2.7 |
  | wallet: `/wallet/@gtg/transfers` and `/wallet/@{observer}/transfers`, from `/wallet/@gtg/transfers`'s limits | 1.5 | 1.9 |

  The performance score has no logged-in limit yet: this measurement did not record it.
  CLS and `lcp-lazy-loaded` are the logged-out limits.
- **Bytes** do not depend on the host: the limit is the logged-in transfer measured here
  plus 10 %. For a route this measurement did not cover, it is that route's logged-out
  median in the integration check at the same revision (`8d3fcbf3`) plus the logged-in
  difference of its page type (284 KB for feeds and posts, 172 KB for the wallet), plus
  10 %. WASM: 966 KB plus 10 % on every logged-in route. Byte limits are rounded up to
  10,000 bytes.
- **Logged-out WASM:** in the integration check's reports of `8d3fcbf3`, `/blog/trending`
  and `/blog/@gtg` load no WASM and `/wallet/@gtg/transfers` loads the wax WASM (947 KB),
  for its reads. The logged-out blog routes have a WASM limit of 0; the wallet has none.
